# Payments — تقرير التنفيذ

التاريخ: 2026-10-04. ربط Vue بعقود Laravel الحالية فقط، دون تعديل Backend أو Old HTML أو إضافة dependency أو مزود دفع. النتيجة: المدفوعات والمعاملات والتحصيل النقدي ومحاولات العميل تعمل عبر API؛ الدفع الإلكتروني غير متاح حاليًا لعدم وجود adapter حقيقي مسجل.

## التقرير المطلوب — 49 نقطة

1. **Backend files inspected:** `routes/api.php`؛ Controllers: `Admin/PaymentController`, `OrderPaymentController`, `PaymentWebhookController`, `OrderController`, `GuestOrderController`؛ Requests: `ListPaymentsRequest`, `InitiatePaymentRequest`, `CheckoutRequest`؛ Resources: `PaymentResource`, `PaymentTransactionResource`, `OrderResource`, `AdminOrderResource`؛ Models: `Payment`, `PaymentTransaction`, `PaymentWebhookEvent`, `Order`؛ Actions: `CollectCashPaymentAction`, `InitiatePaymentAction`, `HandlePaymentWebhookAction`, `SyncOrderPaymentStatusAction`, `PlaceOrderAction`، وآثار cancellation؛ Services: `PaymentProviderManager`, `PaymentStatusWriter`, `PaymentStateMachine`, `PaymentPresentation`, `OrderPaymentPolicy`, `AdminOrderActions`, `Money`, `GuestOrderAccess`؛ Contract: `PaymentProviderInterface`؛ DTOs: `CreatePaymentData`, `PaymentProviderResult`, `WebhookPaymentData`؛ Enums: `PaymentMethod`, `PaymentStatus`, `PaymentTransactionType`, `PaymentTransactionStatus`, `WebhookEventStatus`؛ `PaymentSucceeded`, `PaymentFailed` وlisteners الخاصة بهما؛ `RolePermissionSeeder`, `config/payments.php`, payment-domain migration؛ tests: `CashPaymentTest`, `AdminPaymentTest`, `InitiatePaymentTest`, `PaymentWebhookTest`, `PaymentPolicyTest`, `PaymentStateMachineTest`. لا توجد policy مستقلة للدفع؛ الصلاحيات والملكية داخل middleware/actions/controllers المذكورة.
2. **Actual endpoints:** GET `/api/v1/admin/payments`، GET `/admin/payments/{uuid}`، GET `/admin/payments/{uuid}/transactions`؛ POST `/admin/orders/{uuid}/payments/cash/collect`؛ GET/POST `/orders/{uuid}/payments` للمالك؛ POST `/orders/{uuid}/guest/payments` بـ`X-Order-Token`؛ POST `/webhooks/payments/{provider}` للمزود فقط. لا endpoints refund/cancel-payment/verify/sync/reprocess أو admin webhook listing.
3. **Methods:** Enum يحتوي `cash`, `card`. النقد يعمل فعليًا؛ card له بنية backend دون adapter حقيقي. Checkout يعرض cash فقط، مع بيان عدم توفر الدفع الإلكتروني؛ صفحات السجل تستطيع قراءة/filter مدفوعات card تاريخية لأنها قيمة enum صحيحة. لا mada أو مزود مخترع. لا API حالي يعلن capability/provider readiness؛ قيد نشر الدفع الإلكتروني موثق في utility، ويحتاج إعادة تدقيق عند إضافة provider مستقبلًا. مسار recovery لمحاولة Checkout قديمة يحتفظ بالطريقة الأصلية للتحقق من نتيجة الطلب السابق بدل إنشاء طلب بديل.
4. **Statuses:** `pending`, `processing`, `paid`, `failed`, `cancelled`, `partially_refunded`, `refunded`. العرض العربي وbadge/money helpers مركزي في `utils/paymentStatus.js`؛ `constants/orderStatus.js` يعيد تصدير مساعدات الدفع السابقة للتوافق، دون State Machine في Vue.
5. **Terminal payment statuses:** paid/failed/cancelled/refunded/partially_refunded لا انتقال منها في PaymentStateMachine الحالية. قراءة تفاصيل/محاولات الدفع تحدث دوريًا فقط عند pending/processing. انتهاء فترة انتظار لا يحول الحالة إلى failed.
6. **Payment ↔ Order:** Order hasMany payments، latestPayment منفصلة، Payment belongsTo Order. `OrderResource.payment` ملخص طريقة/حالة الطلب؛ `latest_payment` يظهر عند تحميل العلاقة فقط. paid في محاولة صحيحة بالمبلغ والعملة يزامن ملخص الطلب؛ failed attempt لا يلغي الطلب ولا يساوي بالضرورة `order.payment.status=failed`. order.status مستقل تمامًا.
7. **Payment ↔ Transaction:** Payment محاولة/سجل دفع، hasMany transactions. Transaction عملية مالية داخل المحاولة. الأنواع: authorization/capture/sale/refund/void؛ حالات transaction: pending/succeeded/failed. وجود نوع refund لا يعني وجود API لاسترداد الأموال. الشاشات تفصل قائمة المحاولات عن معاملات المحاولة.
8. **Cash workflow:** Checkout ينشئ pending payment بمبلغ Order النهائي وعملته، provider=null، paid_at=null، دون transaction قبل التحصيل. الاستلام/التوصيل لا ينشئان payment methods منفصلة؛ كلاهما cash. يجوز إكمال طلب نقدي وهو unpaid؛ التحصيل فعل مستقل لاحق. لا Cash=Paid تلقائيًا.
9. **Collection endpoint:** POST `/api/v1/admin/orders/{uuid}/payments/cash/collect`، الجسم `{}` فقط. لا amount/currency/status/timestamps/actor في request من Vue. يعيد PaymentResource الجديدة أو نفس السجل المدفوع عند replay.
10. **Collection permission:** `payments.collect_cash`؛ القراءة `payments.view`. الأدوار الافتراضية manager/super_admin/cashier تملك التحصيل، kitchen/customer لا. الصلاحيات المخصصة من `/admin/me` معتبرة. Order Details يستخدم `available_actions.includes('collect_cash')` مع permission. Payment Details يدعم مستخدمًا يملك payments.view/collect_cash دون orders.view؛ يستخدم method/status المورد ويعيد GET Payment قبل POST، والخادم يقرر أهلية الطلب نهائيًا.
11. **Real online providers:** لا يوجد production adapter مسجل؛ `config/payments.php` يحتوي `providers => []`، ولا implementation حقيقية داخل app. FakePaymentProvider الموجود أصلًا داخل tests فقط، لم أضف مزودًا وهميًا أو استخدمه في Vue.
12. **Provider contract:** supports(method)، createPayment(CreatePaymentData)، retrievePayment(providerPaymentId)، verifyWebhook(rawBody,headers)، parseWebhook(rawBody). Manager يحل driver المسجل؛ عدم وجوده يرجع PAYMENT_PROVIDER_NOT_CONFIGURED 503 قبل إنشاء payment.
13. **Online initiation endpoint:** POST `/orders/{uuid}/payments` أو `/orders/{uuid}/guest/payments`. موجود Backend، لكنه غير مشغّل في واجهة الدفع الحالي لعدم adapter صالح. لا API calls إلكترونية لمجرد محاكاة إمكانية دفع.
14. **Initiation request:** optional `Idempotency-Key` header (1–100 حرف alphanumeric/underscore/hyphen)؛ ownership بالـBearer أو guest header. amount/currency/provider/method/status من Order والـconfig فقط؛ card/card_number/pan/cvv/cvc/payment_token ممنوعة في Request. لا card form في Vue.
15. **Initiation response:** `{payment: PaymentResource, checkout_url: string|null}`. URL تظهر فقط عند pending/processing، وPaymentPresentation تقبل HTTPS مع host دون credentials وحد أقصى 2048 حرفًا. لا client_secret/session_id/public key في العقد الحالي.
16. **Redirect/return:** لم يوجد provider حقيقي أو return route/callback contract لواجهة Vue؛ لم أنشئ `/payment/return` أو redirect أو popup وهميًا. checkout_url في future adapter تأتي من Backend ولا تُبنى في Vue. لا query parameter في الصفحات الحالية يغير الدفع.
17. **Success authority:** PaymentResource/OrderResource بعد عمل Backend. verified provider result قد يثبت paid عند initiation، أو verified webhook يزامنها. العودة من provider أو `?status=success` ليست إثباتًا. Chrome تحقق من تجاهل هذا query حين المورد processing.
18. **Webhook architecture:** Provider → POST `/api/v1/webhooks/payments/{provider}` → manager/verify/parse → safe event → locks/writer/sync/event after commit. Frontend لا تستدعي webhook نهائيًا. اسم المزود محدود بالroute، throttle 120/min وbody limit افتراضي 65536 bytes.
19. **Verification:** adapter يتحقق من التوقيع وصلاحية replay timestamp وفق عقده؛ config tolerance 300 seconds. لا implementation لتوقيع provider حقيقي في الإنتاج. tests السابقة تتحقق من forged/expired signature عبر fake اختبار فقط. لا secrets أو signatures في Vue/VITE/storage.
20. **Webhook idempotency:** fingerprint SHA256 لevent_id أو raw body عند غياب ID، scoped provider؛ unique provider/event وprovider/fingerprint وtransaction operation_key. قفل event؛ processed/ignored/failed events لا تُعاد ماليًا. event Received مع payment غير موجود يبقى لإعادة تسليم provider ويرجع 503. Vue لا تعالج duplicates.
21. **Webhook fields:** Model uuid/provider/provider_event_id/fingerprint/event_type/signature_valid/status/payment_id/payload/processed_at/failure_message/created_at. status enum received/processed/ignored/failed. المخزن safe payload يحتوي status/amount/currency فقط؛ payload/fingerprint/failure_message hidden. لا Admin Resource أو GET endpoint لهذه الأحداث، لذلك لا شاشة خام أو ادعاء visibility جاهزة.
22. **Retry:** Backend يعيد نفس المحاولة عند نفس key، ويسمح new key بعد failed بمحاولة جديدة إذا provider صالح؛ active pending/processing يمنع محاولة متداخلة بـ409. paid يمنع pay again. Vue لم تضف pay/retry زرًا دون provider أو capability contract. يمكن تحديث الحالة فقط؛ لا تحويل Processing إلى Failed من المتصفح.
23. **Idempotency:** initiation identity+order-scoped hashed key وunique DB؛ cash lock order ثم pending/paid payment، replay paid cash يعيد نفس Payment دون sale ثانية؛ webhook كما سبق. لا key مخترع للتحصيل لأنه لا يحتاج header حسب العقد. Timeout التحصيل يظهر عدم التأكد، ثم refetch والتحقق قبل retry؛ لا تكرار تلقائي للعملية المالية.

- تأكيد الطلب مسموح قبل التحصيل للشبكة كما للنقد، وإنشاء الطلب لا يعني الدفع. ينشأ سجل pending بالمبلغ المعتمد من الخادم.
- تسجيل التحصيل يستخدم إجراء التحصيل الحالي وصلاحية الكاشير payments.collect_cash، ويحافظ على التحقق من المبلغ ومنع تكرار التسجيل. تعرض الواجهة طريقة الدفع قبل التأكيد.
- إلغاء الطلب يلغي محاولة الشبكة المعلقة فقط، ولا ينشئ استردادًا تلقائيًا. الشبكة لا تبدأ عملية لدى مزود دفع إلكتروني.
- التكامل يستخدم العقود الحالية دون تغيير الروابط أو أرقام الطلبات أو إضافة بوابة دفع أو حقول بطاقات حساسة.
- نجح بناء الواجهة واختبار المتصفح: اختيار شبكة يرسل network ويعرض شبكة في تأكيد الطلب، مع استمرار اختبارات الأخطاء ومنع التكرار والتجاوب. الإرسال معزول دون شراء فعلي.
