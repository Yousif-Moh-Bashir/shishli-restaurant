# Shishli Finance — تقرير التنفيذ المحلي

> أحدث نتيجة: [معالجة مخاطر الجاهزية](HARDENING.md)، وتشمل اجتياز MySQL والتزامن والمتصفح الفعلي محليًا. لم يبدأ النشر أو التحقق من HTTPS على VPS.

> تحديث المراجعة النهائية: راجع [FINAL_REVIEW.md](FINAL_REVIEW.md) لنتائج إعادة الاختبارات ومخاطر التشغيل والأمان وخطة النشر والتراجع. القرار الحالي **غير جاهز للنشر**. تقرير التنفيذ أدناه يحتفظ بنتائج مرحلة الإنشاء، ولا يمثل إجازة نشر.

تاريخ التقرير: 2 نوفمبر 2026. التنفيذ محلي فقط؛ لم تُعدّل إعدادات الإنتاج أو بياناته، ولم يُنفّذ نشر أو اتصال بـVPS. لم تُشغّل Migration أو Seeder على قاعدة التطوير أو الإنتاج. تشغيل الترحيلات والبذور أثناء الاختبارات اقتصر على SQLite في الذاكرة.

## 1. الفحص والبنية

- الخلفية: `back-end`، والإصدارات المثبتة عند الفحص Laravel 13.33.0، Sanctum 4.3.3، Spatie Permission 8.3.0، PHP 8.3.29.
- الواجهة: `front-end`، مع Vue وPinia وVue Router وAxios وVite الحالية، دون إضافة اعتماد JavaScript.
- المستخدمون والفروع يستخدمون معرفات UUID في API، ومفاتيح رقمية داخلية في العلاقات.
- المصادقة الحالية تستخدم Sanctum Bearer Tokens، وأُعيد استخدام `/api/v1/login` و`/api/v1/logout` وطبقة Axios الحالية.
- بوابة إدارة المطعم كانت تقبل أي صلاحية غير خاصة بالسائق. أضيف استثناء `finance.*` إلى هذا الشرط حتى لا تمنح الصلاحيات المالية وصولًا إداريًا للمطعم.
- سجل `AdminActivityLog` الحالي غير قابل للتعديل، لكن خدمة تسجيله ترشح حقولًا محدودة؛ لذلك أُنشئ سجل مالي مستقل لحفظ تفاصيل المصادر والمبالغ والإصدارات والتصحيحات.
- كانت حالة Git نظيفة عند البداية. لم يُستخدم reset أو clean أو checkout لاستبدال ملفات المستخدم، ولم تُغيّر إعدادات Git العامة. عولج اختلاف ملكية المستودع باستثناء خاص بالأوامر الجارية.

## 2. قاعدة البيانات وAPI

الجداول الجديدة فقط:

| الجدول | الاستخدام |
| --- | --- |
| `finance_branch_user` | توزيع الوصول المالي على الفروع |
| `finance_revenue_sources` | مصادر الإيراد القابلة للإدارة والتعطيل |
| `finance_expense_categories` | تصنيفات المصروفات |
| `finance_suppliers` | الموردون |
| `finance_revenue_days` | يوم مالي واحد لكل فرع وتاريخ |
| `finance_revenue_lines` | مبالغ المصادر ضمن اليوم |
| `finance_expenses` | المصروفات المدفوعة المسجلة يدويًا |
| `finance_purchases` | فواتير المشتريات المدفوعة المسجلة يدويًا |
| `finance_audit_logs` | العمليات المالية والقيم السابقة والجديدة |

الترحيل الجديد لا يغيّر جداول الطلبات أو المدفوعات أو التوصيل أو المخزون، ولا يستورد بيانات منها. ترتبط السجلات بالفروع والمستخدمين الحاليين بقيود مفاتيح خارجية تمنع حذف المراجع المالية.

### السلوك المالي

- المبالغ مخزنة في `DECIMAL`، وتُجمع بأجزاء العملة الصحيحة بدل الحساب بالفاصلة العائمة. يُرفض السالب والدقة الزائدة والصيغة الأسية وتجاوز حجم المبلغ.
- قيد فريد على الفرع والتاريخ، وقيد فريد على المصدر داخل اليوم. إنشاء سجل اليوم يقفل صف الفرع داخل معاملة، والاعتماد والتصحيح يقفلان صف اليوم.
- الإجمالي وحالة السجل ومنشئه ومعتمده تُحدد على الخادم. الحقول الإضافية المرسلة من العميل لا تستطيع اعتماد السجل أو استبدال الإجمالي.
- الاعتماد ينقل المسودة إلى حالة معتمدة، والتعديل العادي للمعتمد مرفوض. التصحيح يحتاج صلاحية مستقلة وسببًا موثقًا وإصدارًا حديثًا، ويبقى السجل معتمدًا.
- رقم إصدار يحمي الإيرادات والمصروفات والمشتريات من الكتابة فوق تحديث أحدث؛ التعارض يرجع `409`.
- فواتير المورد الواحد لا تتكرر برقم الفاتورة نفسه. تبقى المصروفات والمشتريات منفصلتين في التخزين والتقارير.
- المرفقات PDF/JPG/PNG حتى 10 ميغابايت، مخزنة في القرص الخاص `local`، وتنزيلها يتطلب صلاحية الوحدة والوصول إلى الفرع. لا يعيد API مسار التخزين.
- التقارير تستخدم الإيرادات المعتمدة فقط، وتطرح المصروفات والمشتريات كلًا مرة واحدة. تعرض «صافي التدفق المسجل»، وليس صافي الربح المحاسبي.
- المرحلة الحالية تسجل مدفوعات المشتريات والمصروفات، ولا تدير آجال الموردين أو الاستحقاقات أو تكلفة البضاعة أو الضرائب أو دفتر أستاذ محاسبيًا.
- فلتر المصدر يحدد الإيرادات؛ المصروفات والمشتريات غير موزعة على مصادر الإيراد. هذه القاعدة مكتوبة في التقرير وملفات التصدير.
- اليوم المالي الافتراضي يتبع `Asia/Riyadh`، ويمكن تخصيصه عبر `FINANCE_TIMEZONE` دون تغيير توقيت نظام الطلبات. العملة الحالية SAR.
- التقارير يومية وشهرية وسنوية، مع مقارنة بفترة سابقة مساوية في عدد الأيام. التصدير يتضمن نطاق الفرع والمصدر والعملة والتوقيت.
- Excel ملف XLSX فعلي، بخلايا مالية رقمية وأسماء نصية تمنع تنفيذ صيغ المستخدم. PDF فعلي يدعم العربية وRTL عبر mPDF، الذي أضيف بموافقة المستخدم.

### الصلاحيات

| الدور | الصلاحيات الافتراضية |
| --- | --- |
| `finance_entry` | عرض الإيرادات وإنشاؤها وتعديل مسوداتها، عرض/إنشاء المصروفات والمشتريات، عرض الموردين؛ ضمن الفروع المحددة |
| `finance_accountant` | صلاحيات الإدخال، وتعديل المصروفات والمشتريات، وإدارة الموردين، والتقارير والتصدير؛ ضمن الفروع المحددة |
| `finance_manager` | جميع الصلاحيات المالية، والاعتماد والتصحيح والإعدادات والمستخدمون والتدقيق وجميع الفروع |

الصلاحيات تبدأ بـ`finance.*`. لا يضيف Seeder المالي أي صلاحية طلبات أو منتجات إلى الأدوار المالية، ولا يمنح مدير المطعم صلاحيات مالية تلقائيًا. إعادة تشغيل Seeder لا تعيد ضبط أدوار مالية موجودة أو تفعّل مصادر معطلة.

واجهة المستخدمين تنشئ حسابات مالية وتحدد الدور والفروع والحالة. تُلغى الجلسات عند تعديل الحساب. يمنع الخادم خفض صلاحية المستخدم لنفسه أو تعطيله، ويحمي آخر مدير مالي نشط. الحسابات المشتركة مع أدوار أو صلاحيات غير مالية لا يمكن تغيير بياناتها عبر إدارة المستخدمين المالية.

المسارات تحت `/api/v1/finance`؛ جميعها تتطلب المصادقة و`finance.access`، مع التحقق من صلاحية العملية والفرع على الخادم. سجل التدقيق لا يوفر مسارات تعديل أو حذف. القراءة والتصدير الماليان يستخدمان `Cache-Control: private, no-store`.

## 3. واجهة Vue — BACKEND → FRONTEND COVERAGE

لم توجد واجهة مالية سابقة. أُنشئ مدخل مستقل `finance.html` وبناء مستقل `dist-finance`، مع إعادة استخدام Axios ومسارات المصادقة وشعار وألوان شيشلي. بيانات الجلسة المالية منفصلة في `sessionStorage`.

| ميزات الخلفية الموجودة/المنفذة | الواجهة المنفذة |
| --- | --- |
| مصادر الإيراد، حفظ المسودة، الإجمالي، الاعتماد، التصحيح، الإصدار | قائمة الإيرادات، فلاتر الحالة والتاريخ والفرع والمصدر، نموذج المبالغ والإجمالي، تأكيد الاعتماد، سبب التصحيح |
| المصروفات والتصنيفات والدفع والمرفقات | قائمة ونموذج مصروف، تحميل المرفق الخاص، سبب تعديل السجل |
| المشتريات والموردون ومنع تكرار الفاتورة | قائمة ونموذج فاتورة مدفوعة، رقم الفاتورة والمورد والمرفقات، إدارة الموردين وتعطيلهم |
| تقارير مجمعة ومقارنة فترات وتصدير | لوحة مؤشرات، اتجاه الإيرادات، جدول الفترات، ملخص المصادر، فلاتر، تنزيل PDF/XLSX |
| إنشاء وتعديل مستخدم مالي ودوره وفروعه وحالته | صفحة المستخدمين ونموذج حساب مالي ووصف صلاحيات الأدوار |
| إضافة وتعديل وتعطيل المصادر والتصنيفات | تبويبات الإعدادات المالية |
| التدقيق والقيم السابقة والجديدة | صفحة السجل مع المستخدم والتوقيت والسبب وتفاصيل التغيير |
| ترقيم الصفحات وأخطاء التحقق والصلاحيات | قوائم مرقمة، تحميل وحالات فارغة، أخطاء عربية، منع الإرسال المكرر، تأكيد العمليات الحساسة |

الفجوات التي اكتُشفت عولجت: مدخل مستقل، جلسة مالية، مسارات وصول مستقلة، مصادر وتصنيفات قابلة للإدارة، تصحيح الإقفالات، تنزيل المرفقات، التقارير والتصدير، وإدارة المستخدمين. إصلاح API المالي من نفس النطاق يمنع وراثة عنوان API الخاص ببيئة واجهة المطعم. تحديث صفحات التطوير مباشرةً يقدم المدخل المالي دون الوقوع في مدخل المطعم.

العمليات الداخلية غير المعروضة عمدًا: المفاتيح الرقمية، مسارات الملفات، حساب الإجمالي الموثوق، أقفال المعاملات، وتعديل/حذف سجل التدقيق. لا توجد واجهة مالية لتحرير الطلبات أو المنتجات أو المدفوعات أو المخزون.

اختبار Chrome يستخدم خادم نقل وهميًا معزولًا، ولا يدّعي أنه اختبار متصفح متصل بقاعدة Laravel حية. اختبارات Laravel تختبر API الحقيقية والتخزين والمعاملات داخل قاعدة اختبار. راجعت لقطات سطح المكتب والجوال، ولا توجد أخطاء JavaScript أو طلبات متجهة إلى إنتاج في اختبار المتصفح.

فشل سابق تحققت منه: `InternalDeliveryTest::test_full_workflow_reuses_payment_and_tracks_unsettled_cash`، السطر 333، يطلب مسار إكمال إداري بحساب سائق ويتوقع `409`، بينما بوابة الإدارة ترفضه بـ`403`. تكرر الفشل بعد إعادة شرط الوصول الأصلي مؤقتًا، ثم استعدت التعديل المالي. لم أغيّر اختبار التوصيل أو منطق الطلبات لمعالجة هذا التوقع.

`composer audit` أبلغ عن تنبيه متوسط موجود مسبقًا في `symfony/mime`: `CVE-2026-45070`. لم تُحدّث هذه الحزمة ضمن إضافة المالية. يلزم تقييمه ومعالجته كتحديث اعتماد منفصل قبل الإصدار.

## 6. التشغيل المحلي والتحقق المتبقي

إعادة اختبارات API لا تتطلب أي قاعدة بيانات دائمة:

```powershell
cd back-end
php vendor/bin/phpunit -c phpunit.finance.xml
```

ملف الاختبار يفرض SQLite في الذاكرة، مع حواجز تمنع تشغيل الترحيلات الاختبارية على قاعدة غير معزولة.

اختبارات وبناء الواجهة من `front-end`:

```powershell
npm run test:finance
npm run build:finance
npm run test:finance:browser
npm run build
```

اختبار المتصفح يعيد استخدام أداة Chrome الموجودة في المشروع، ويتوقع Chrome على مساره الحالي في Windows. لقطات التشغيل تتولد داخل `.finance-check`.

للتطوير، شغّل `npm run dev:finance`. يستخدم مدخل المالية ومساراته، ويوجه API إلى Laravel المحلي على المنفذ 8000. عند استخدام Docker المحلي، اضبط `FINANCE_DEV_API_ORIGIN` إلى عنوانه المحلي قبل تشغيل Vite. لا تغيّر هذه القيمة API الإنتاج؛ البناء المالي يستخدم `/api/v1` من نفس النطاق.

قبل الاستخدام التفاعلي تحتاج قاعدة تطوير مؤكدة ومحلية إلى تطبيق الترحيل الجديد وSeeder المالي، ثم منح حساب قائم دور المدير المالي عبر `finance:grant-manager`. **لم أنفذ خطوات تهيئة قاعدة دائمة، ولم أنشئ بيانات دخول افتراضية.** أمر المنح يتطلب تأكيد Laravel في بيئة الإنتاج، أو علم `--force` للعملية المصرح بها صراحةً.

عند توافر Docker يمكن تشغيل اختبارات MySQL بمعزل كامل:

```powershell
docker compose -f docker/compose.finance-test.yaml up --build --abort-on-container-exit --exit-code-from finance-tests
```

هذا الملف لا يقرأ ملفات بيئة الإنتاج ولا يستخدم أحجامه أو شبكاته. قاعدة MySQL اختبارية داخل tmpfs، واسم المضيف والقاعدة يُتحقق منهما قبل الترحيلات، بما فيها في عمليات الاختبار الفرعية. حالات التزامن تنفذ طلبي HTTP في عمليتي PHP منفصلتين، وتتحقق من انتظار القفل ومنع التكرار أو تجاوز رقم الإصدار.

إعداد النطاق الفرعي في المرحلة الخامسة مُجهز فقط: واجهة Nginx مالية مستقلة على منفذ حلقي 8089، ومسارات API محددة للمصادقة والمالية، وحظر التخزين العام وواجهات المطعم على ذلك المضيف. `finance-proxy.conf.example` قالب للوكيل الأمامي وTLS. لم يُثبّت القالب، ولم تُغيّر DNS أو الشهادات أو ملفات الخادم الحالية.

المتبقي قبل إعلان الجاهزية للإصدار: تنفيذ اختبارات MySQL والتزامن، وبناء صور Docker والتحقق من Nginx وTLS في بيئة مرحلية، ومراجعة تنبيه الاعتماد السابق. محرك Docker غير متاح في هذه الجلسة، لذلك لم أعتبر نجاح صياغة Compose دليلًا على نجاح تشغيل الحاويات. أي تهيئة إنتاج أو نشر تتطلب موافقة صريحة منفصلة.
