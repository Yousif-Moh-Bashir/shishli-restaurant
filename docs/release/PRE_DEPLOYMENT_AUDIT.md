# SHISHLI — Phase 1: Pre-deployment readiness audit

تاريخ التدقيق: 2026-10-11. النطاق: `back-end/` و`front-end/` وبيئة اختبار محلية. لم يُنفذ نشر خارجي أو دفع أو إرسال رسائل حقيقية، ولم تُستخدم قاعدة المطعم للاختبارات أو الترحيلات. احتُفظ بتغييرات المستخدم السابقة ولم يُعدل مجلد `Şişli`.

## القرار

التطبيق مناسب للانتقال إلى **تجهيز Docker والتحقق على staging** لمسار الطلب النقدي. هذا لا يعني جاهزية استقبال عملاء الإنتاج. يجب استيفاء [عوائق الإطلاق](RELEASE_BLOCKERS.md)، وDocker Engine غير متاح في هذه الجلسة. لم يُختبر Oracle MySQL؛ الخادم المتاح يستخدم بروتوكول MySQL وهو MariaDB 10.4.25.

## ما فُحص فعليًا

- قرئت تعليمات المشروع وتقارير `docs/qa/` و`docs/performance/` قبل اختيار الاختبارات. نتائجها السابقة مراجع تاريخية وليست اختبارات نُفذت اليوم.
- فُحصت المسارات الفعلية، Sanctum، طلبات التحقق، موارد العميل والمندوب، وضع الطلب، التحصيل والتسويات، استعلامات القائمة والتقارير، ساعات العمل، إعدادات الإنتاج والـ seeders.
- Laravel المثبت 13.33.0، Sanctum 4.3.3، PHP 8.3.29، PHPUnit 12.5.35، Vite 8.3.2. لم تتغير الاعتمادات.
- أُنشئت قاعدة عشوائية معزولة `shishli_perf_*`، وشُغلت عليها migrations وDemoDataSeeder في `testing` فقط: 44 ترحيلًا، 63 جدولًا، 81 مفتاحًا أجنبيًا. لا توجد سجلات يتيمة في `branch_products` أو روابط فروع المندوبين المفحوصة. [الدليل](evidence/database.json).
- فُحصت فهارس الطلبات والمنتجات والسلة والتحصيل والتسويات، وخطط EXPLAIN لطلبات يوم العمل وقائمة الفرع والمندوب. لم يوجد دليل يبرر إضافة فهرس جديد للبيانات الصغيرة الحالية.
- شُغلت اختبارات وظائف على قاعدة MariaDB جديدة منفصلة عن قاعدة قياس الأداء، مع التحقق من اسمها والاتصال قبل تشغيل أي اختبار يستخدم RefreshDatabase. أزيلت تلك القاعدة المؤقتة فقط بعد التنفيذ. [دليل العزل](evidence/mysql-functional-isolation.json).
- قِيست الصفحات الثماني المطلوبة قبل/بعد، على Development وProduction منفصلين، وقِيست عشرة endpoints بسبع عينات لكل endpoint في كل مرحلة. [النتائج والمنهج](PERFORMANCE_BEFORE_AFTER.md).

## المشاكل والإصلاحات الحالية

1. **CORS الإنتاج:** كانت إعدادات Laravel الافتراضية تسمح بـ `*` ولا تقرأ allowlist خاصة بالمشروع. أضيف `config/cors.php` مع `CORS_ALLOWED_ORIGINS`. الإنتاج يبدأ بلا مصادر cross-origin مسموحة ما لم تضبط؛ local/testing يحتفظان بالتوافق الحالي. CORS لا يغني عن المصادقة ولا يمنع استدعاء API من برامج غير المتصفح.
2. **قراءة Retry-After:** الواجهة تقرأ هذا الرأس عند 429، لكن CORS لم يعرضه للمتصفح عبر مصدر مختلف. أضيف إظهار `Retry-After` و`X-Request-ID`. اختُبر ذلك عبر استجابة HTTP فعلية داخل اختبار Laravel.
3. **إعداد الوكيل:** أضيف `config/trustedproxy.php` لقراءة IPs/CIDRs محددة من `TRUSTED_PROXIES`، دون تفعيل الثقة العامة. اختبارات scheme/IP تتحقق من قبول رؤوس الوكيل الموثوق ورفض تزويرها من غيره. يلزم اختيار عناوين النشر الحقيقية في المرحلة الثانية.
4. **اختبار ترقيم الطلب على MySQL:** فشل توقع `SH-0001` بعد معاملات سابقة؛ عداد auto-increment لا يعود مع rollback. أُصلح الاختبار ليتحقق من صيغة الرقم، اختلاف رقمَي طلبين مع وقت ثابت، وحفظهما مع UUID الصحيح. لم تتغير طريقة ترقيم التطبيق أو بياناته.
5. أُنشئ نموذج إعداد إنتاج بلا أسرار. أدوات القياس أصبحت تقبل مسار تقرير منفصل وعدد عينات اختياريًا؛ لم تُستبدل الأدلة التاريخية.

الصور الكبيرة QA-006 أُصلحت **قبل هذه الجلسة** في العمل الموجود: البناء الحالي يستعمل WebP للشعار والخلفية. لم يُنسب هذا الإصلاح إلى المرحلة الحالية، ولم تُعد ضغط الصور أو تغيير التصميم أو إضافة Redis.

## مراجعة الأمان وحدودها

أعيد التحقق من حماية seeding الإنتاج ورفض DemoDataSeeder، وحدود API والخصوصية والتحصيل وwebhook. فحصت validation الصور، الموارد، responses العامة، وعدم تتبع `.env` الحقيقي في ملفات Git المفحوصة. اختبارات webhook تثبت سلامة المزود الاختباري فقط. مراجعة الاعتمادات السابقة لا تمثل فحص advisories جديدًا اليوم، ولم يُفحص تاريخ Git كاملًا أو صلاحيات نظام الإنتاج.

لم تُراجع قاعدة المطعم الحالية لحذف/تعطيل حسابات تجريبية قديمة؛ يجب فحص قاعدة الإصدار المقصودة قبل استقبال العملاء. tokens في localStorage وغياب expiry افتراضي يبقيان موضوعي تحسين أمنيين موثقين. صلاحيات upload/storage وHTTPS وproxy والتشغيل والنسخ الاحتياطية يجب اختبارها على staging.

## BACKEND → FRONTEND COVERAGE

الوظائف الموجودة تشمل التسجيل والقائمة والسلة والخصومات والعناوين والطلب والمطبخ والمندوب والتحصيل والتقارير؛ راجعت واجهاتها ومصادر API الفعلية. الواجهة لا تعرض الدفع card دون مزود، والخادم يبقى مصدر السعر والصلاحيات والانتقالات. لم تُضف واجهة جديدة: الميزات الناقصة OTP/recovery/GPS تحتاج نطاق تنفيذ مستقل. مزودو الدفع والإرسال ومفاتيح التشغيل والـ workers خصائص داخلية لا تُعرض للمستخدم كحقول إعداد أسرار.
