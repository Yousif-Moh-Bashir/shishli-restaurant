# Operational readiness

2026-10-11. البيانات الحالية في الاختبارات اصطناعية. وجود seeders وواجهات إدارة لا يثبت اعتماد قيم تشغيل المطعم الحقيقية.

| المجال | ما يجب اعتماده وإدخاله فعليًا | حالة التنفيذ |
|---|---|---|
| المطعم | الاسم، الهاتف، البريد، العملة، المنطقة الزمنية، الحد الأدنى والضرائب إن انطبقت | settings موجودة؛ البيانات الفعلية تحتاج اعتماد |
| الفروع | موقع دقيق ورقم التواصل، is_active/accepts_orders، دعم الاستلام والتوصيل | CRUD موجود؛ لا تكرر BranchSeeder على بيانات مخصصة دون مراجعة |
| ساعات العمل | ساعات كل يوم، ساعات تتجاوز منتصف الليل، آخر موعد طلب، الاستثناءات والعطلات | خدمة schedules/closures مختبرة؛ يجب إدخال القيم الفعلية |
| نطاق التوصيل | مناطق/إحداثيات التغطية، الرسوم والحد الأدنى وعتبة الإعفاء | quote/checkout يعيدان التحقق على الخادم |
| المنتجات | السعر والأوصاف والصور والمجموعات المطلوبة وتوفر كل فرع | branch pricing وoptions مختبران؛ راجع القائمة المنشورة |
| CMS | محتوى home/about/contact/الشروط والصور ونشر الصفحات المطلوبة | CMS seeder ينشئ draft؛ الاختبار ينشر صفحات اصطناعية فقط |
| المخزون | الرصيد الافتتاحي ووحدات القياس ووصفات الاستهلاك وسياسة نفاد المخزون | البرمجيات موجودة؛ الرصيد الحقيقي NOT VERIFIED |
| وسائل الدفع | اعتماد cash؛ network فقط إذا توفر جهاز وإجراء تحصيل واضح | card الإلكتروني غير معروض؛ لا مزود حقيقي |
| المناديب | حساب فعلي مستقل، فرع، enabled/available، تدريب على قبول/استلام/توصيل | عزل الفرع والخصوصية والتزامن مختبرة |
| الصلاحيات | أول super_admin آمن، موظفون فعليون وأدوار manager/cashier/kitchen بأقل صلاحيات | لا يُنشأ أول admin بالإنتاج تلقائيًا؛ لا تستخدم حساب demo |
| التحصيل والتسويات | عهدة المندوب، المبلغ الدقيق، مواعيد التسوية ومسؤول الكاشير | سجل مستقل ومنع التكرار مختبران؛ تحصيل المندوب cash فقط |
| الإلغاء والفشل | أسباب إلزامية، توقيت السماح بالإلغاء، إعادة الإسناد/المحاولة، حفظ العهدة | المسارات مختبرة؛ الإجراءات البشرية تحتاج اعتماد |
| الطلبات غير المدفوعة | متى يؤكد الطلب وكيف يسجل التحصيل ومتى يمنع الإكمال | cash/network يسمحان بالتأكيد قبل الدفع؛ الإلكتروني يحتاج paid؛ delivered يحتاج paid |
| الإشعارات | استخدام لوحة الإدارة والمطبخ والمتابعة؛ اختيار إرسال خارجي إن لزم | لا تعد العميل بوصول SMS/WhatsApp/email الآن |
| التقارير | المسؤول عن إقفال اليوم ومطابقة الإيرادات وتسويات المندوب | completed_sales بتاريخ إنشاء الطلب؛ collected_revenue بتاريخ التحصيل؛ لا تخلطهما |

## إجراء الإطلاق النقدي

1. اعتماد وإدخال بيانات المطعم/الفرع والجدول ومناطق التوصيل والقائمة والصور والمخزون، ونشر الصفحات المطلوبة.
2. تجهيز حساب إدارة آمن وحسابات موظفين ومناديب فعلية؛ مراجعة/تعطيل حسابات الاختبار القديمة في قاعدة الإصدار المقصودة إن وجدت. لم يُعدل التدقيق قاعدة المطعم الحالية.
3. إجراء طلب cash تجريبي مضبوط على staging: قائمة الفرع → خيارات → سلة → عنوان/quote → checkout → مطبخ → مندوب → تحصيل → delivered/completed → settlement → مطابقة التقارير.
4. تجربة الفرع المغلق، المنتج غير المتاح، عنوان خارج المنطقة، إلغاء الطلب، فشل التسليم وإعادة المحاولة قبل استقبال العملاء.
5. تعيين مالك للاستجابة للطلبات/الفشل ومراقبة queue/logs/backup، واعتماد سياسة إقفال اليوم واسترداد المدفوعات offline.

**شبكة والتوصيل:** الواجهة تعرض network كدفع لدى المطعم، والمندوب لا يملك عملية تحصيل شبكة؛ يلزم اتفاق تشغيلي على الجهاز ومن يسجل الدفع بصلاحية التحصيل قبل إتمام التسليم. إذا لم تتوفر هذه العملية، يجب حسم نطاق شبكة عند الإطلاق قبل استقبال الطلبات بدل افتراض أنها دفع إلكتروني جاهز.

**فروع الموظفين:** مدير/كاشير/مطبخ لديهم الصلاحيات المسندة على مستوى النظام الحالي؛ لا يُدّعى عزلهم التلقائي حسب الفرع. عند اشتراط عزل عام للموظفين يصبح ذلك مطلبًا قبل إطلاق متعدد الفروع، أما المندوب فعزله موجود ومختبر.

**نظرة عامة:** تستخدم اليوم افتراضيًا وفق timezone المطعم وتسمح بتغيير الفترة. إدارة الطلبات والمطبخ تستخدم يوم العمل الذي قد يعبر منتصف الليل؛ لا تعادل فترة التقارير التقويمية تلقائيًا. المخزون لقطة حالية مستقلة عن فلتر الفترة. يلزم تدريب الإدارة على الفرق عند مطابقة الأرقام.

اعتماد المطعم لهذه القيم والسياسات **NOT VERIFIED**؛ لا تعتبر البيانات الاصطناعية أو نجاح الاختبارات موافقة تشغيلية.
