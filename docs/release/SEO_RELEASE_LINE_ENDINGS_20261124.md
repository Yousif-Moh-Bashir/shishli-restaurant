# إصدار Shishli المنشور وحماية نهايات الأسطر

بحسب تأكيد التشغيل، نُشر فرع `release/seo-security-20261124` عند `91f81e48cd948a9abc335ab2f841519531313f63` على VPS. فشل تشغيل Laravel أولًا بسبب CRLF في `docker/php/entrypoint.sh` داخل نسخة البناء. حُوّل الملف إلى LF على الخادم وأُعيد بناء الصورة بنجاح. الإعداد المعتمد للإصدار هو `SEO_PRERENDER=false`. لم تُجر هذه المهمة اتصالًا بخدمات الإنتاج أو تغييرًا على قاعدة البيانات.

## الحماية للإصدار التالي

- تفرض `.gitattributes` نهايات LF على امتدادات Shell وملفات Docker وCompose وإعدادات الحاويات النصية. تُطبّق على الملفات عند تسجيلها وإعادة استخراجها في Git، وقد يحتاج ملف سبق استخراجه بصيغة CRLF إلى إعادة حفظه بـLF. تجنّب إعادة تطبيع المستودع كاملًا في مساحة العمل المتباينة.
- يقرأ Dockerfile سكربت الدخول بالبايت ويرفض بناء التطبيق إذا وجد CR. يفحص صياغته باستخدام `/bin/sh -n` قبل منحه إذن التنفيذ. فحص البناء الكامل يحتاج محرك Docker محليًا.
- يضيف سير CI فحصًا على Windows وLinux لملفات Shell وDocker، بما فيها الملفات التي تُعرف بترويسة shebang. يضبط مغلّف SEO إعدادات Git لكل أمر على `core.autocrlf=false` و`core.eol=lf`، ويرفض نشر الأرشيف إذا كانت **بايتاته بعد الاستخراج** تحتوي على CR. استخدام `git archive` مع commit محدد يمنع انتقال ملفات العمل والأسرار المحلية إلى الحزمة، مع قائمة إدخال محصورة ومراجعة الملفات التي قد تحتوي على أسرار أو SQLite. قواعد Git الجديدة وحدها لا تغيّر بايتات commit قديم.

### أوامر البناء والتغليف

تشغّل من جذر نسخة Git المحلية مع Node.js وGit و`tar` على PATH. اختر ملف إخراج جديدًا، واحتفظ ببصمة SHA-256 التي يطبعها الأمر.

```text
node --test docker/tests/linux-line-endings.test.mjs
node docker/check-linux-line-endings.mjs
node docker/package-seo-release.mjs <approved-commit> <new-source.tar.gz>
```

للحزم التاريخية، افحص المجلد المستخرج بالأمر `node docker/check-linux-line-endings.mjs --directory <staging-directory>` قبل البناء أو النقل. تحقّق من SHA-256 بعد النقل.

## نتيجة التحقق المحلي

- نجح اختبارا Node، بما فيهما رفض أرشيف من commit يسجّل CRLF وقبول نظيره بعد التصحيح، مع محاكاة `core.autocrlf=true`.
- اجتاز الفحص 74 ملف Shell وDocker. وُحّدت نهايات الأسطر دون تعديل المحتوى في `.dockerignore` و`compose.yaml` و`docker/ci/compose.php-runtime.yaml` وملفات Compose الخاصة بالإشعارات ومنع ازدواج التوصيل وإصدار التوصيل وتجربة الطلب، وأربعة ملفات Dockerfile وdockerignore لتجربة الطلب، و`docker/nginx/Dockerfile` و`default.conf` و`e2e.conf`، و`docker/php/Dockerfile`. بعض هذه الملفات كانت مسجلة أصلًا بـLF في فهرس Git.
- أعاد المغلّف بناء أرشيف تحقق محلي من commit المنشور وفحص 19 ملفًا داخل الأرشيف المستخرج. بصمته `d01efc568941b4426bbeaa831644fa11fc77e7fa38007b55a6f8499fe74fbbcc`.
- نفّذت بيئة Shell محلية سطر الحماية نفسه، فرفض CRLF وقبل LF، ثم نجح تشغيل سكربت الدخول في وضع الاختبار. كان محرك Docker المحلي غير متاح، لذلك بقي بناء الصورة الكامل وتشغيل CI على GitHub غير متحققين في هذه المهمة.

### التحقق النهائي على فرع الإصدار

- نجح بناء صورتي الاختبار `shishli-crlf-verify-app:local` و`shishli-crlf-verify-nginx:local` على Docker Desktop بمحرك Linux. رفض بناء App سكربت CRLF، ثم نجح بعد تصحيح نهايات الأسطر.
- نجح سكربت الدخول في وضع الإنتاج، بما يشمل تجهيز ذاكرة إعدادات Laravel ومساراته وقوالبه. اجتاز PHP-FPM وNginx فحوص الإعدادات، وأعاد Nginx الحالة HTTP 200 للمسارات `/` و`/up` و`/robots.txt`. أظهر Laravel 13.43.0 القيمة `seo.prerender=false`.
- شُغّلت الحاويتان على شبكة داخلية بلا منافذ منشورة، مع SQLite في الذاكرة وإعدادات اختبار مؤقتة. أُزيلت حاويتا الاختبار وشبكتهما بعد الفحص.
- نجح اختبارا Node وفحص 38 ملفًا في نسخة فرع الإصدار. بيّنت المقارنة مع commit النشر أن التغييرات المسجلة تقتصر على الوقاية والتغليف والتوثيق. سير GitHub Actions ينتظر الرفع.

## خطة مزامنة المصادر على الخادم

1. من جلسة إدارية مصرح بها، سجّل commit الإصدار المنشور ومعرّفات صور التشغيل وأسماء خدماتها وملفات Compose الفعلية. أنشئ نسخة احتياطية مقيدة من فروق مصدر الخادم، بما فيها ملفات الطباعة الثلاثة وCompose وNginx وملف الوكلاء الموثوقين وملفات إعداد Finance. احفظ ملفات البيئة والأسرار في النسخ المقيدة داخل الخادم، وتجنب طباعة قيمها أو رفعها إلى Git.
2. حضّر مجلد مراجعة جديدًا تحت `/opt/shishli-releases` من commit المنشور أو أرشيفه المتحقق. احتفظ بمصدر الإنتاج الحالي في `/opt/shishli` أثناء المقارنة. قارن توقيع سكربت الدخول وبايتاته قبل البناء، وسجّل تصحيح LF الذي طُبق على المصدر عند النشر.
3. ادمج فروق المصدر التشغيلية المعتمدة في نسخة المراجعة فقط. تحقّق من قواعد HTTPS وقبول الموظف في الطباعة، وربط ملف الوكلاء الموثوقين من المضيف، ومدخل Finance وشبكاته، وخدمات الطابور والجدولة. استخدم Compose الفعلي أو طبقة صور ضيقة فوقه. افحص `docker compose config --quiet`، وقارن أسماء الشبكات والمنافذ ونقاط الربط ووحدات التخزين بعد حجب الأسرار.
4. عند اعتماد المزامنة لاحقًا، طبّق فقط فرق الملفات الموافق عليه. لا تنفّذ `git pull` أو `reset` أو `clean` فوق مساحة الإنتاج المتباينة. افصل مزامنة المصدر عن استبدال الحاويات، واحتفظ بـ`SEO_PRERENDER=false` صراحةً. أي بناء قادم يبدأ من الحزمة النظيفة ويمر بفحص LF و`nginx -t` وتجربة تشغيل التطبيق.
5. عند فشل المرشح، أعد وسم الصور السابقة من جرد التشغيل وطبّق ملف التراجع فوق Compose الفعلي للخدمات التي استُبدلت فقط. تحقّق من الصحة والطابور والفوترة والطباعة. تحفظ قاعدة البيانات ووحدات التخزين، ولا تُستعاد نسخة DB قديمة فوق الطلبات الحديثة كإجراء تراجع عادي.
